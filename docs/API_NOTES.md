# Backend contract for frontend work

Scope: static inspection of route registration/handlers, input schemas, auth/access code, error handling, Prisma field types, Supabase config, and shared-package public exports/declarations. Business service implementations, tests, migrations, and package implementation bodies were not inspected; the app, builds and tests were not run. Public contract declarations describe intended response fields; service-produced responses and service-only checks are not independently verified here.

## Connection and authentication

- API origin defaults to `http://127.0.0.1:3001` (`PORT`, bound to loopback); every endpoint below has prefix `/api/v1`.
- API startup uses server-only `DATABASE_URL`, `SUPABASE_URL`, optional `SUPABASE_PUBLISHABLE_KEY` (needed for legacy HS256 and invitation email verification), and `SUPABASE_SERVICE_ROLE_KEY` for photos. Never expose database/service-role credentials to the browser.
- No frontend environment variable is defined by backend code. Suggested new Vite convention: `VITE_API_BASE_URL=/api/v1` with a same-origin development proxy to the API; this is a recommendation, not existing configuration. No CORS plugin/allow-list or OPTIONS handler is registered; direct cross-origin bearer requests need a proxy or approved backend CORS work.
- Protected routes require `Authorization: Bearer <Supabase access token>`; the API neither reads nor sets session cookies. JSON mutations use `Content-Type: application/json`.
- No API login, logout, signup, session, or refresh endpoints exist. `GET /me/contexts` lists available workspaces, not an auth session. A frontend-only API auth flow therefore cannot currently be implemented without an additional auth integration decision.
- Verification uses Supabase issuer `${SUPABASE_URL}/auth/v1`, audience/role `authenticated`, UUID subject, and expiration; anonymous identities are rejected. ES256/RS256 use JWKS; legacy HS256 uses Supabase's `/auth/v1/user` verification.
- Missing, invalid, or expired tokens return 401 `UNAUTHENTICATED`, with `WWW-Authenticate: Bearer`; API does not refresh tokens. Auth infrastructure failure returns 503 `AUTH_UNAVAILABLE`. Supabase config sets JWT lifetime to 3600 seconds and refresh-token rotation on (10-second reuse interval).
- Store access requires an active organization membership AND active store assignment, checked against PostgreSQL on requests; invalid/inaccessible scope returns 403 without revealing its existence. Roles are `OWNER` and `SALESPERSON`.
- Both assigned roles reach product/sale handlers. Organization management is owner-oriented via the shared owner guard; individual service calls to that guard are outside this inspection. Product detail exposes acquisition cost and cost per gram to owners and to salespeople when `salespersonCanViewAcquisitionCost` is enabled (default false).
- Protected route group sends `Cache-Control: private, no-store`. Health is public.
- The API requires a verified Supabase `session_id` claim. Owners can restrict their current session with `POST /organizations/:organizationId/stores/:storeId/salesperson-mode` (204, idempotent). The access response includes `salespersonDisplay: true` for a restricted session and still returns the actual membership role. The restriction follows token refreshes and all stores in that session. The web app returns to Owner mode by signing in again through Supabase with the owner's password. The previous session stays restricted.
- Restricted sessions receive neither acquisition values nor owner product capabilities, even when the organization lets staff view acquisition costs. Settings, team administration and owner inventory mutations return 403. Product intake still accepts the required acquisition rate, and product search and sales remain available. Apply migration `202611200002_salesperson_display_session` before starting this API version.

## Errors and validation

- Application errors contain `code` and `message`, with an optional `field`. `SALE_CONFIRMATION_REQUIRED` also includes `confirmation`. Messages are Azerbaijani.
- 400: `INVALID_ONBOARDING`, `INVALID_MEMBERSHIP`, `INVALID_SETTINGS`, `INVALID_PRODUCT`, `INVALID_CUSTOMER`, `INVALID_SALE`, `SALE_PAYMENT_TOO_LOW`, `SALE_PAYMENT_NOT_DUE`, `SALE_CUSTOMER_REQUIRED`.
- 401: `UNAUTHENTICATED`; 403: `ACCESS_DENIED`.
- 404: `PRODUCT_NOT_FOUND`, `SALE_NOT_FOUND`, `CUSTOMER_NOT_FOUND`.
- 409: `INVITATION_UNAVAILABLE`, `PURITY_CONFLICT`, `PRODUCT_CODE_CONFLICT`, `PRODUCT_EDIT_CONFLICT`, `PRODUCT_DELETE_CONFLICT`, `PHOTO_CONFLICT`, `SALE_CONFLICT`, `SALE_CONFIRMATION_REQUIRED`, `CUSTOMER_DELETE_CONFLICT`.
- 503: `AUTH_UNAVAILABLE`, `PHOTO_UNAVAILABLE`; unexpected errors in protected group become 500 `INTERNAL_ERROR` with `{code,message}`.
- No registered route supplies Fastify JSON Schema and no Zod schema is used. Validation is manual: shared `parseOnboarding`, `parseProductCreate`, `parsePurity`, `parseRate`, route checks, auth UUID checks, and backend `parseSaleInput`. TypeScript interfaces alone do not validate requests.
- Invalid onboarding is a direct 400 `{code,message}` response; product/sale validation may include `field`, others usually do not. No validation issue array exists. Non-`AccessError` failures (including malformed JSON in the protected plugin) map to 500 instead of preserving their Fastify status. Unmatched routes/default Fastify errors outside this handler can use Fastify's `{statusCode,error,message}` shape.
- Route-level validation gaps: `GET /health` has no input checks; `GET /me/contexts` checks identity only; membership listing, invitation revoke/resend, member activate/deactivate and store assign/remove do not validate params locally; settings GET does not validate params locally.
- Product detail/photo-upload and sale detail delegate ID checks; sales listing delegates query validation; product/sale options validate scope only; onboarding/product/rate parsers and service-only checks are not audited beyond their public entry points. These are inspection limits, not proof that downstream validation is absent.

## Numbers, lists, retries

- Money and weights in public contracts are decimal **strings**; never use `parseFloat`. Money object (`Money`) is `{amount:string,currency:string}`. AZN uses 2 minor-unit digits; existing code supports other ISO currencies, so do not assume every amount is AZN.
- Sale input enforces currency minor-unit precision, weight up to 3 decimal places (12 integer digits), exchange rate up to 8 (12 integer digits), and amount up to 16 integer digits. Purity is an integer JSON number, 1–999 (fineness), not a fractional percentage. Product/purity options also return numbers.
- Weight uses `Decimal(15,3)`. Acquisition totals and item sale prices use `(20,4)`. Acquisition cost per gram uses `(35,16)`. Sale totals and payment amounts use `(28,4)`. Gold rates use `(18,4)`, exchange rates `(24,8)`, settlements/change/converted amounts `(32,4)`, and trade-in calculated/accepted values `(32,15)`.
- Response contracts declare strings but do not promise fixed trailing-zero padding; preserve exact values. `roundMoneyHalfUp` is exported, but service calculation/rounding implementation was not inspected.
- Product list query: `organizationId`, `storeId`, optional `q` (trimmed, max 160), `status=IN_STOCK|SOLD`, `category` (max 80), `purity` (integer query string), `after` (nonempty, max 80), `facets=1`. Other `facets` values act as false. NUL is rejected in q/category/after.
- Sale list accepts scoped `q`, `date`, `after`; their validation, date timezone, cursor encoding, page sizes, and ordering are service-defined and unverified. Both list contracts return `{items,nextCursor?}`; pass `nextCursor` unchanged as `after`. No route-level limit/page/sort convention is exposed; do not invent one.
- `POST /sales` and `POST /sales/:id/payments` require an `Idempotency-Key` matching `[A-Za-z0-9._:-]{1,128}`. Preserve the key and payload on uncertain retries. Checkout keys are scoped to organization, store and actor. Repayment keys are additionally scoped to the sale. An identical replay returns the current receipt, and a changed payload returns `SALE_CONFLICT` on `idempotencyKey`.

Product acquisition accepts a positive weight with up to 3 fractional digits and a positive rate with up to 16 fractional digits in a supported ISO currency. The API calculates weight × rate and rounds the total half up to 4 decimal places, independent of currency minor units. A total that rounds to zero or exceeds 16 whole digits is invalid. The product form uses the same shared parser for its preview. The migration derives rates from positive stored weight and cost while preserving original totals. A rate may be absent for legacy records with invalid values. Apply migration `202611200001_product_acquisition_per_gram` to the target database before starting this API version. Product details depend on the new column.

Acquisition edits and deletions require an active owner with access to the store. Edits are limited to in-stock products with no sale or movement beyond initial intake. Deletion returns `PRODUCT_DELETE_CONFLICT` for sold products or any sale or inventory dependency, including `PRODUCT_ADDED`. Every API-created product has an intake movement. The schema has no product archive.

Movements are nested in product detail, and old-gold trade-ins and payment history are nested in sales. The sales API has no cancellation or void workflow.

### Official exchange rates

- Owners can select AZN, USD, EUR and TRY in Settings and choose the default for new sales. An existing legacy currency remains available to its organization. The payment list must include the default. Checkout and repayment validate saved currency selections. The inventory widget displays selected CBAR currencies. Changing currency settings preserves the denomination and applied rates on existing receipts. Migration `202611230001_payment_currencies` adds the selection. Organizations with no saved selection keep their existing API payment compatibility.

- The [Central Bank of Azerbaijan rates page](https://www.cbar.az/currency/rates?language=en) publishes the current bulletin link for application imports. The dated feed is at `https://cbar.az/currencies/DD.MM.YYYY.xml`. The public requests need no API key. The provider page specifies no request quota and says the most recently published bulletin remains effective on weekends and public holidays.
- The backend follows the published date and validates the XML's `ValCurs Date` and the USD, EUR and TRY `Valute` entries. It divides each `Value` by `Nominal` using decimal arithmetic and stores AZN per unit at up to eight decimal places, rounding half up if required by that precision.
- Apply migration `202611220003_official_exchange_rates` before starting this API version. The synchronized Task 13 API checks the provider once every 24 hours and atomically saves the full snapshot. The PostgreSQL cache shares the last attempt and snapshot across stores, API instances and restarts. Each document request has a three-second timeout and at most one retry. A failed or invalid refresh preserves the saved snapshot and marks it stale. A successfully verified bulletin may remain current across non-publication days.
- `ExchangeRatesResponse` is `{snapshot,stale}`. A snapshot includes `source:"CBAR"`, `effectiveDate` (ISO calendar date), `retrievedAt` (ISO timestamp), and `rates:{USD,EUR,TRY}` as decimal strings. Before the first successful retrieval, `snapshot` is null and `stale` is true. Inventory and payment forms share the store-scoped browser cache.
- Checkout and repayment forms suggest the latest available official rate and allow manual overrides. The payment-preview endpoint validates the submitted tender and returns its AZN equivalent rounded half up to two places. The existing sale and repayment endpoints persist the submitted rate and amount with the payment. Refreshing official rates only updates the rate cache.

### Gold prices

- An active purity without a store selling rule uses its fresh market reference as the selling rate. An owner-saved rule takes precedence. Product selling estimates use net gold weight and convert to the organization's default currency at the latest applicable CBAR rate for USD, EUR or TRY. New store buying rules are deferred. Existing trade-in rates remain available.

- Gold API's current XAU spot feed is free, keyless and has no published request quota. Its abuse policy can block excessive traffic. The provider says it updates every 30 seconds and falls back across multiple upstreams. It offers no availability or accuracy guarantee. Commercial app use is permitted and attribution is optional. Historical and OHLC endpoints share a separate free limit of 10 requests per hour. The app uses only the current endpoint, which returned a live USD quote during evaluation on November 22, 2026. [Pricing](https://gold-api.com/pricing) · [FAQ](https://gold-api.com/faqs) · [Terms](https://gold-api.com/terms)
- The API defaults to `MIZAN_GOLD_PRICE_PROVIDER=gold-api`. Set it to `off` to stop outbound gold requests. Any saved quote remains visible as stale and fixed prices remain available. Apply migrations `202611220004_gold_prices` and `202611220005_store_gold_pricing` before serving these routes.
- The default `MIZAN_GOLD_PRICE_SYNC=interval` starts a timer in a running API process on startup. It checks for due gold and FX refreshes once a minute. PostgreSQL claims and fences each refresh across all instances. Scheduled-mode requests read from PostgreSQL. If the host sleeps or suspends background work, the timer cannot guarantee updates during that period. Set `MIZAN_GOLD_PRICE_SYNC=on-demand` to let the first authorized market, pricing Settings or exchange-rate read after the relevant interval claim a shared refresh.
- Gold refreshes are due after 15 minutes, for up to 96 normal requests per day per database. Each attempt times out after three seconds. Transport errors and HTTP 5xx get one retry. Invalid data, older quotes, and an unavailable applicable FX rate leave the last successful observations intact. A failed refresh, overdue check, or market observation older than 24 hours marks the quote stale. The provider timestamp reflects its upstream fetch, which can repeat a pre-closure price. A verified CBAR bulletin stays applicable on non-publication days.
- The API normalizes USD per troy ounce using the CBAR USD/AZN rate and `31.1034768` grams per troy ounce. The CBAR bulletin must be effective on or before the quote's Baku calendar date. Each distinct observation includes original price, source and effective timestamp, first retrieval timestamp, exchange rate and bulletin date, and AZN per gram rounded half up to eight decimals. Purity rates multiply the stored amount by fineness divided by 1,000. Dashboard reference prices round half up to two decimals. The cache records the last successful retrieval as a separate timestamp.
- `GoldMarketPrices` is `{quote,stale,references}`. The quote is null before a valid import and otherwise includes `id,source,effectiveAt,retrievedAt,usdPerTroyOunce,usdAzn,exchangeDate,normalizedAznPerGram,pricePerGram`. Each active purity has a `{purity,pricePerGram}` reference. Owners also see `rules` for their selected store. Both history endpoints return up to 50 entries ordered newest first and an opaque `nextCursor` if more are available. Market history accepts inclusive `from` and `through` dates in `YYYY-MM-DD` using Asia/Baku.
- `GoldPricingChange` requires `purity,kind,mode,value,expectedPriceId`. Preview and save accept `kind:"SELL"`. `value` is an exact decimal string with up to four fractional digits. The `FIXED` mode uses that amount in AZN per gram. `PERCENTAGE` multiplies the purity rate by `1 + value / 100`. `OFFSET` adds the specified AZN per gram. The effective operational rate rounds half up to four decimals. The preview returns `{pricePerGram,quoteId?}`. Send the preview's `quoteId` when saving a relative rule. Fixed values and resulting rates must be at least zero. A relative rule that would produce a negative rate after a market change is unavailable until the market recovers or the rule changes.
- Store rules append a version attributed to the owner. Send `expectedPriceId:null` for a first rule. A changed quote or rule returns `GOLD_PRICE_CONFLICT` (409), a missing or stale market quote for a relative rule returns `GOLD_PRICE_UNAVAILABLE` (409), and an inactive purity returns `PURITY_CONFLICT`. Fixed rules are independent of market availability.
- Product intake and acquisition editing accept optional `netGoldWeight` in grams with up to three decimal places. An acquisition edit can pass null to clear it. Product detail reports material value in AZN and the selling estimate in the default sale currency when applicable. Existing records with unknown net weight have no estimate. Checkout accepts the final edited amount. Existing AZN store buying rules take precedence over legacy old-gold rates when available. A market-linked trade-in sends the `marketQuoteId` returned by `GET /sales/options` along with `rateId`. The ledger stores the agreed rate and amount and links rule-priced trade-ins to the rule version and, when applicable, market quote.

### Public response/request field reference

- `OnboardingResult`: `organizationId,storeId,membershipId`. `StoreContext`: `organizationId,organizationName,storeId,storeName,role`.
- `MembershipDirectory`: `stores:{id,name}[]`, `invitations:InvitationSummary[]`, `members:{userId,email:string|null,status,storeIds:string[]}[]`.
- `InvitationSummary`: `id,email,storeId,status,expiresAt`; status `pending|accepted|expired|revoked`; delivery `sent|failed|not_sent`; member status `active|inactive`.
- `OrganizationSettings`: `defaultCurrency,salespersonCanViewAcquisitionCost`; `PurityGrade`: `value,active`; `OldGoldRate`: `id,purity,currency,amountPerGram,effectiveAt,current`; `TradingSettings`: `settings:OrganizationSettings,purities:PurityGrade[],rates:OldGoldRate[]`.
- `ProductListItem`: `id,code,name,category,purity,weight,status,hasOutstandingDebt?`. Products transferred at checkout always have `status:SOLD`. The API returns `hasOutstandingDebt:true` while their associated sale has an unpaid balance, and omits the flag when settled. The `SOLD` filter includes both. `ProductList`: `items:ProductListItem[],nextCursor?,filters?:{categories:string[],purities:number[]}`.
- `ProductDetail`: ProductListItem + `acquisitionCost?:Money,acquisitionCostPerGram?:Money,canEditAcquisition?:boolean,canDelete?:boolean,note:string|null,createdAt,photo:{url,contentType,size}|null,movements:{id,kind,actorId,createdAt}[],sale:{id,total:Money,createdAt}|null`. The edit and delete capabilities are sent only to owners. Movement kinds: `PRODUCT_ADDED|PRODUCT_SOLD|OLD_GOLD_RECEIVED`.
- `ProductPhotoUpload`: `uploadId,uploadUrl`; signed upload transport/content restrictions and confirmation response are service-defined, not established by route code alone.
- `SaleCreateInput` accepts 1–100 distinct `items:{productId,saleAmount}[]`, or the original single-item `productId,saleAmount` fields. Final negotiated prices use the organization currency and may be zero. Optional fields include `expectedCurrency`, up to 100 `tradeIns:{purity,weight,rateId,overrideAmount?}[]` and up to 20 `payments:SalePaymentInput[]`. Omit `payments` to record the balance as cash, or send `[]` to record zero monetary payments. An `expectedCurrency` mismatch returns `SALE_CONFLICT` on `currency`.
- `SalePaymentInput` is `{method,currency,amount,exchangeRate?}`. Methods are `CASH|CARD|TRANSFER`. Each amount must be positive in a supported ISO currency. For AZN, the rate is one and may be omitted. Other currencies require AZN per one unit of payment currency. Linked non-AZN sales and non-AZN sales with explicit payments require `customerReportingRate` (AZN per unit of sale currency). Supply it for anonymous non-AZN cash sales to capture the AZN equivalent too.
- The API rounds the signed balance (sale total minus accepted trade-in credit) half up to the sale currency's minor units. If positive, it applies the monetary payments to that balance. Each payment stores the original amount, currency and rate. Its AZN equivalent is rounded half up to two places. For a different-currency payment on a non-AZN sale, the API divides the unrounded AZN equivalent by the sale's saved reporting rate and rounds half up to sale currency minor units. A payment in the sale currency credits its original amount.
- Positive debt requires a store-scoped `customerId` (`SALE_CUSTOMER_REQUIRED`). `SALE_PAYMENT_TOO_SMALL` means a payment rounds to zero in the sale currency. `SALE_PAYMENT_EXCEEDS_BALANCE` means the converted payments exceed the amount due. `SALE_PAYMENT_NOT_DUE` means no balance is available to collect. Legacy checkout accepts the singular `payment` with a rate in sale currency and retains its cash-change behavior. Legacy `recordDebt:true` still allows omitted tender. Use one checkout format per request.
- `SalePreviewInput` accepts `tradeIns`, optional `saleAmounts,expectedCurrency,payments,customerReportingRate`. When sale amounts are supplied, the result includes `saleAmount,amountDue,paidAmount,outstandingDebt,overpayment` and per-payment `convertedAmount,amountAzn` when applicable. It returns exact `tradeInTotal` and trade-in line values. Preview uses current trade-in rates and writes no data.
- An outstanding balance or below-cost item returns 409 `SALE_CONFIRMATION_REQUIRED` before any writes. The challenge returns `token`, optional `debt:{total,tradeIn,paid,outstanding}` as Money values and an optional `belowCost:true`. Owners in Owner mode also receive `financials:{currency,losses:{productId,code,acquisitionCost,saleAmount,expectedLoss}[]}` for below-cost items. After explicit user confirmation, retry the same payload and key with `Sale-Confirmation: <token>`. The token binds the request, actor session and amounts. Present a fresh challenge if returned. API restarts invalidate pending tokens.
- `SaleResult` contains ordered `items:{product,saleAmount,profit?}[]`, the first item as `product`, and `tradeInTotal,balance,payout,tradeIns,paidAmount,outstandingDebt,paymentStatus,payments`. `paidAmount` is net monetary credit to the sale in its currency. `paymentStatus` is `PAID` if nothing remains due, `UNPAID` if the entire post-trade-in balance remains due, and `PARTIALLY_PAID` otherwise. Each payment includes `id,kind,method,currency,amount,exchangeRate,amountAzn,convertedAmount,change,createdAt`. `kind` is `CHECKOUT|REPAYMENT`. Historical receipts retain `payment`; their method and an unavailable AZN equivalent may be null.
- Repayments append a payment and reduce only the specified sale's outstanding balance in one transaction. They leave the original sale amount, profit and inventory movements unchanged. Concurrent repayments are checked against the balance remaining at commit. Apply migration `202611220002_sale_debt` before starting this API version. It backfills linked receipts from stored settlement and tender and treats anonymous legacy sales as settled.
- Profit fields are returned only to an owner in Owner mode, regardless of the staff product-cost setting. `profit` includes `acquisitionCost:Money|null,grossProfit:string|null,marginPercent:string|null`. Item profit also includes `acquisitionCostPerGram:Money|null`. Gross profit uses the final sales value less the sale-time cost snapshot. Trade-ins, payouts, tender and change settle the sale value. Margin is gross profit divided by final sales value, expressed as a percentage rounded half up to two places. Zero-value sales have no margin.
- Older receipts have no acquisition snapshots and display unavailable profit. When a cost is missing or is in a different currency from the sale, the API leaves gross profit and margin unavailable. A known cost retains its original currency. Aggregate cost requires known costs in a single currency across all items. Apply migration `202611200003_sale_items` before starting the updated API.
- `SaleList` entries retain the first product snapshot and include `itemCount,paymentStatus,outstandingDebt`. The search matches any sold item's name or code. List entries omit profit.

### Customers

- `CustomerContact` contains `id,name,phone`. Name is required and limited to 120 characters. Phone is required and accepts 3–15 digits with an optional leading plus and formatting spaces, parentheses, or dashes.
- `CustomerDetail` adds `note:string|null` to the summary. Notes may be up to 1,000 characters and preserve line breaks. On edit, an omitted note preserves the saved value. A blank or null note clears it.
- `CustomerSummary` adds `totalPurchases:Money,outstandingDebt:Money,lastPurchaseAt:string|null`. The API sums the original sale totals and current sale balances using each sale's stored reporting rate, then rounds each aggregate to two AZN decimal places. Repayments reduce customer debt without adding purchases.
- `CustomerList` supports `q` (maximum 160 characters, case-insensitive name or normalized phone substring) and `after`. `CustomerHistory` supports `after`. Both return up to 50 rows ordered by creation time descending with an ID tie-breaker. Pass `nextCursor` unchanged as `after`.
- Each purchase contains `id,createdAt,productName,itemCount,total:Money,tradeInCredit:Money,paidAmount:Money,outstandingDebt:Money,payment:Money|null`. Settlement totals use the sale currency. The legacy `payment` field contains single checkout tender when present. The linked receipt shows checkout and repayment history under the existing receipt permissions.
- Both assigned roles can read, add and edit store contacts. Deletion requires Owner mode. Any linked receipt blocks deletion with `CUSTOMER_DELETE_CONFLICT`. Apply migration `202611220001_customers` before starting the updated API. Existing unlinked receipts remain anonymous.

## Findings / inspection limits

- Browser integration is incomplete: no CORS registration, API auth/session endpoints, or backend-defined frontend env names; proxy/Auth configuration needs an explicit implementation decision.
- Error behavior is inconsistent: non-AccessError failures become 500, field hints are optional, and unmatched routes can use Fastify's default envelope.
- No route JSON Schema/OpenAPI exists; local validation gaps and delegated validation are listed above. Several response fields/options and pagination rules require a later targeted service inspection.
- The product checks above cover owner access, acquisition-cost redaction and arithmetic, and deletion safeguards. The broader inspection did not review service transactions, arithmetic or idempotent replay outside this product scope.
- Existing organization/store roles and the multi-currency contract remain documented as shipped.
