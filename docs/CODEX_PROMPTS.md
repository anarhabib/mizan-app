## Prompt 0 — Backend contract notes (read-only, run once)

Reasoning: medium. Branch: `task/0-api-notes`.

```text
Task 0: write docs/API_NOTES.md, a compact backend contract for frontend work. Read-only on the backend: do not change any backend code.

Read AGENTS.md first. Inspect only: Fastify route files and their schemas, the auth/session code, the error handler, the CORS config, and the Prisma schema for field types. Also check the role of the supabase/ folder (read config files only) and list the names and exports of packages/* (do not read their internals). Do not read tests, migrations or node_modules.

Write docs/API_NOTES.md (max 150 lines) with:
1. Base URL, API prefix, how the frontend should be configured (env var names).
2. Auth: login/logout/session endpoints, mechanism (cookie or bearer), how expiry and 401 behave, roles and what each role may do.
3. Error format: exact JSON shape, error codes used, validation error shape.
4. Number formats: how money (AZN), weights (grams) and gold purity are serialized (string or number), and their precision.
5. Pagination, filtering, sorting conventions.
6. Idempotency: whether any mutation supports an idempotency key. If not, say so.
7. Endpoint table: method, path, purpose, role required, request body fields, response fields. Group by module (items, inventory movements, sales, returns, old-gold exchanges, stock adjustments, customers, reports, users, etc.). Include only endpoints that exist.
8. OpenAPI: say whether a spec is exposed and where.
9. Validation: how routes validate input (Fastify JSON Schema, Zod, manual, none). List routes with no validation as findings, do not fix them.
10. Supabase and shared packages: what supabase/ is used for (hosting only, auth, storage, migrations), whether the frontend would ever need to talk to Supabase directly (it should not), and whether packages/* contain types or schemas that apps/web could import.
11. Findings: anything risky for the frontend (floats used for money, missing transactions, missing permission checks, inconsistent errors). One line each.

Do not run the app, builds or tests. Branch task/0-api-notes, commit, push, open a PR to main. Do not merge. Report in under 10 lines, including the findings.
```

## Prompt 1 — Frontend foundation

Reasoning: high. Branch: `task/1-frontend-foundation`.
Run it after the manual scaffold (see the runbook) and after Prompt 0 is merged.

```text
Task 1: frontend foundation for apps/web. Branch: task/1-frontend-foundation.

Read AGENTS.md, docs/FRONTEND.md and docs/API_NOTES.md first. Ignore DESIGN.md (outdated). From PROJECT_CONTEXT.md read only the module list and navigation section. Do not read backend code, .next or node_modules.

apps/web is already scaffolded (Vite, React, TypeScript, Tailwind v4, shadcn initialized and base components added, package name "web"). Do not reinstall or rewrite shadcn components. Add dependencies only if missing: @tanstack/react-query, @tanstack/react-router and its Vite plugin, react-i18next, i18next, react-hook-form, @hookform/resolvers, zod, decimal.js, vitest.

Build only this foundation, nothing feature-specific:

1. Tooling: enable React Compiler in the Vite config if not enabled. Strict TypeScript extending the root tsconfig.base.json where compatible, "@/" alias, VITE_API_URL env var added to the existing .env.example (no secrets). Use the root eslint.config.mjs and prettier setup: extend the root ESLint config to cover apps/web (typescript, react-hooks), remove any ESLint or Prettier config generated by Vite inside apps/web, and delete apps/web/README.md if present. Add `dev`, `build`, `lint`, `typecheck` and `test` scripts to apps/web/package.json if missing.
2. API layer (shared/lib/api): thin fetch wrapper using the auth mechanism and error format from API_NOTES.md. Normalize failures to one ApiError (status, code, message, optional field errors). If API_NOTES.md says an OpenAPI spec exists, do not generate a client: note it in your report for my decision.
3. App providers (app/): QueryClient with staleTime 30s, retry 1 for queries only, refetchOnWindowFocus false, mutations never retried. Query devtools in dev only.
4. Auth: login route, session query, route guard redirecting unauthenticated users to /login, logout, 401 handling. The UI may hide controls by role, but never rely on that for security.
5. i18n: react-i18next, Azerbaijani default, English supported, one namespace per feature, typed keys, language switcher in the shell. All strings go through t().
6. Shell: bottom navigation on mobile (max 5 items), sidebar on lg, compact top bar, content max-w-5xl, safe-area insets handled. Nav items come from PROJECT_CONTEXT.md; each routes to an empty placeholder page. Branding is provisional and may change. Render the logo only through one BrandMark component in shared/ui: if an SVG already exists in the repo, move or copy it to src/assets/brand/mizan.svg and use it; otherwise render a plain text wordmark "Mizan". Do not redraw or invent a logo. The single accent color is a temporary deep emerald (#0f5b4a) set only through the --primary token (with a readable --primary-foreground and a lighter variant for dark mode). Neutral warm-gray palette otherwise. Tokens as CSS variables in the Tailwind v4 theme, light and dark. No component may hardcode a color; use semantic tokens only.
7. Shared components: PageHeader, EmptyState, ErrorState (with retry), ListSkeleton, Money and Weight display components. Follow docs/FRONTEND.md UI rules.
8. shared/lib: decimal helpers (decimal.js, values stay strings, no rounding unless an explicit argument says so) and Intl formatters for AZN, grams and purity with explicit units. Vitest tests covering rounding, zero, negative, large values, trailing zeros and string inputs.
9. Platform guidance: before writing the shell and tokens, run `pnpm dlx modern-web-guidance retrieve <id>` for exactly these three guides and apply them: form-factor-adaptation, navbar, color. The CLI saves each guide to a temp file and prints its path: read that file once with your file-reading tool (do not use cat or head) and do not re-read it. Do not search for or retrieve any other guides.
10. Delete the old DESIGN.md and write a new one (max one page): first line exactly `Status: current`, then tokens, density, shell behavior, shared components and their states, and a "Rebranding" line saying exactly where the logo and the accent color live.

Out of scope: feature screens, public or catalog routes, SSR, PWA, backend changes, new abstractions.

Verification: `pnpm --filter web exec tsc --noEmit`, lint on changed files, vitest for shared/lib. Then one visual pass of the shell and the login page at 390px and 1280px, light and dark. No repeated builds.

Finish with: files created, checks run and results, anything unverified, open questions. Then commit, push and open a PR to main. Do not merge.
```

Do not profile in a browser: review the code for unnecessary re-renders (state too high, inline props to memoized children, context for fast-changing values), fix real issues by moving state down, and report anything you suspect. Do not add memoization blindly; I will check with the React DevTools profiler.
